# Лабораторна №5 — Чому GIL впливає на паралельну індексацію

**Машина й умови:** MacBook Air, Apple M4 (10 фізичних / 10 логічних ядер), macOS, CPython 3.13.18 і CPython 3.13.18t без GIL; 1002 текстові документи; медіана трьох запусків на конфігурацію. Індексували з позиціями термінів.

## 1. Конкурентність, паралелізм і GIL

Конкурентність — це організація кількох задач, що просуваються незалежно; паралелізм означає їхнє одночасне виконання на різних ядрах. Звичайний CPython використовує Global Interpreter Lock: у межах одного процесу лише один потік одночасно виконує Python-байткод. Це найбільше заважає CPU-bound задачам (токенізації, підрахунку частот, побудові структур даних). Під час очікування I/O потоки можуть бути корисними й за GIL.

GIL не гарантує атомарності логічної операції `counter[x] += 1`: це прочитати, обчислити та записати. Для коректності потрібен `Lock` або — як у нашому індексаторі — окремі локальні структури воркерів і детерміноване об'єднання.

## 2. Що показав звичайний CPython 3.13

Послідовний запуск: **0.3513 с**. 4 потоки: **0.3413 с**, 8 потоків: **0.3524 с** — практично немає масштабування. 8 процесів: **0.2578 с**, тобто **1.36×** проти serial. В окремих процесів свої інтерпретатори та свої GIL, отже Python-код може справді виконуватися на кількох ядрах паралельно.

Виграш оплачено CPU та пам'яттю: serial — **0.3440 CPU-с** і **85.8 MiB parent peak RSS**; 8 процесів — **1.2512 CPU-с** і **92.1 MiB parent peak RSS**. CPU-вимір враховує завершені дочірні процеси, а RSS у таблиці — лише батька, тому витрати пам'яті системи на всі процеси можуть бути вищими за наведене число. Передавання часткових індексів між процесами включає pickle і міжпроцесний обмін даними.

## 3. Закон Амдала й об'єднання часткових індексів

Навіть якщо індексація шматків добре розпаралелюється, залишаються нерозпаралелені дії: запуск і координація воркерів, передавання результатів, merge та збереження. Закон Амдала в ідеалізованій формі:

\[
S(N) \leq \frac{1}{(1-p)+p/N},
\]

де `p` — частка роботи, яку можна розпаралелити. Для 8 процесів merge зайняв **0.0097 с** при wall time **0.2578 с**. Це помітна, але не єдина послідовна витрата. Збільшення з 8 до 10 процесів не допомогло (0.2578 → 0.2656 с), оскільки накладні витрати й конкуренція за ресурси переважили виграш.

Ці дані не дозволяють точно оцінити `p` тільки за одним виміром merge — частина серіальних і синхронізаційних витрат знаходиться поза ним.

## 4. Що змінилося в CPython 3.13t без GIL

Окрему free-threaded збірку встановлено через `uv python install 3.13t`. Перевірка `sys._is_gil_enabled()` повернула **False**. На відміну від стандартного CPython, Python-код різних потоків тепер може виконуватися паралельно.

Послідовний 3.13t — **0.4256 с** (повільніше за serial стандартного Python 0.3513 с). Але **4 потоки без GIL — 0.1933 с**: це **2.20× відносно serial 3.13t** та приблизно **1.82× відносно serial стандартного CPython**. 2 потоки: 0.2614 с (1.63×), 8 потоків: 0.3333 с (1.28×), 10 потоків: 0.3586 с (1.19×). Найбільша кількість потоків не найкраща: інтерпретатор, алокатор, розподіл навантаження та конкуренція за кеш/пам'ять також мають ціну.

Для 4 потоків без GIL виміряно **0.5950 CPU-с**, **106.5 MiB parent RSS**, merge **0.0096 с**. Без GIL потоки можуть одночасно використовувати кілька ядер, тому CPU time може бути більшим за wall time.

## 5. Контрольована гонитва даних

Скрипт `python -m findex.race_demo` запускає два потоки, які збільшують спільне значення `Counter["hits"]`. `threading.Barrier(2)` **навмисно змушує обидва потоки прочитати попереднє значення до запису**. Через це частина інкрементів втрачається навіть під GIL. На free-threaded Python виміряно:

```text
GIL enabled: False
Expected: 2000; unsynchronized (forced interleaving): 1000; locked: 2000
```

Після обгортання інкременту в `with threading.Lock:` втрат немає. Це *контрольована демонстрація*, а не оцінка ймовірності випадкової гонитви за звичайного планування потоків. Основний індексатор уникає конфліктів, будуючи незалежні часткові результати й об'єднуючи їх після завершення воркерів.

## 6. Практичний висновок

На цьому Apple M4 найкращий результат у стандартному CPython дали **8 процесів (0.2578 с, 1.36×)**; у Python 3.13t — **4 потоки (0.1933 с, 2.20× відносно 3.13t serial)**. Процеси обходять GIL, але мають витрати на створення та pickle; потоки без GIL економлять міжпроцесну передачу даних, проте потребують правильної синхронізації спільного стану. В обох випадках виграш обмежують послідовна частина алгоритму та накладні витрати.
